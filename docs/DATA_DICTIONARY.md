## 2. Relational model

Two hierarchies share one frame index.

**Event hierarchy** — every event belongs to exactly one chance:

```
game (game_id)
 └── period (1..N; 5+ = overtime)
      └── possession (possessions.id)          one span of team control
           └── chance (chances.id)             one scoring opportunity
                ├── touch (touches.id)         one player's continuous control
                │    ├── dribble               dribbles.touch_id
                │    ├── pass                  passes.touch_id
                │    ├── shot                  shots.touch_id
                │    └── action markings       picks / drives / handoffs /
                │                              isolations / posts / closeouts
                ├── off_ball_screen            (screener + cutter touches)
                ├── rebound / turnover / foul / free_throw / timeout
                ├── chance_player  (1 row per player on court, both teams)
                └── matchup        (defender→attacker assignment intervals)
```

**Tracking hierarchy** — one row per tracked entity per frame:

```
game (game_id)
 └── frame (frame_idx, 25 fps since the start of the video)
      ├── home player × 5   xyz, speed, predError, isDetected
      ├── away player × 5   (arrays are EMPTY on dead-ball frames)
      └── ball              xyz (z is a real height), speed, predError
```

**The join between them.** An event's `frame` / `start_frame` *is* the tracking
`frame_idx`. Both also carry `wall_clock` (ms since the start of the video) on
the same origin. So:

```sql
-- the tracking snapshot at the moment of a shot
SELECT t.* FROM tracking_players t JOIN ev_shots s
  ON t.game_id = s.game_id AND t.frame_idx = s.start_frame;
```

Possession context is attached to tracking by interval join
(`possession.start_frame <= frame_idx <= possession.end_frame`) in
`src/tracking/context.py`; 97–99 % of player-frames fall inside a possession.

### Two coordinate frames, and the transform between them

This is the single most important thing to get right, and the repository docs
state it only in prose. Verified empirically here on all 1,459 shots:

* **Event tables** (`location`, `endLoc`, `passerLoc`, …) are in the
  **attacking frame**: the offensive hoop is always at `x = -40.76`,
  the defensive hoop at `+`, and the attacking team's left is `+y`.
* **`tracking_data`** is in the **broadcast frame**: x runs left→right from the
  camera and which hoop a team attacks depends on the period.
* `possessions.leftHoop` bridges them. Joining every shot to the shooter's
  tracking position at its `startFrame`:

| `leftHoop` | n | median &#124;Δx&#124; | median &#124;Δy&#124; | transform |
|---|---|---|---|---|
| `true` | 728 | 0.0000 ft | 0.0000 ft | identity |
| `false` | 730 | 0.0000 ft | 0.0000 ft | `(x, y) → (−x, −y)` — a 180° rotation, **not** an x-flip |

The match is exact, not approximate: the 99th percentile of |Δx| is 1.43 ft on
the `true` side and 0.00 ft on the `false` side, and the residual comes from a
handful of shots whose `startFrame` sits one frame off the tracked release.

Implemented in `src.preprocessing.court.broadcast_to_attacking`, tested in
`tests/test_court.py::test_transform_matches_the_delivered_event_coordinates`.
Coordinates are never mutated in place — normalised values go to new `*_att`
columns.

### Court regions (as delivered) and shot zones (ours)

Delivered `region` vocabulary, 14 values: `left corner three`, `left corner two`, `left wing three`, `left wing two`, `backcourt`, `far`, `middle three`, `middle two`, `key`, `ra`, `right wing three`, `right wing two`, `right corner three`, `right corner two`.

This project also assigns each location a **zone** using the vocabulary of the
season aggregates so that game-level and season-level views line up: `restricted_area`, `paint_non_ra`, `mid_range`, `corner_3_left`, `corner_3_right`, `wing_3_left`, `wing_3_right`, `top_3`, `backcourt`, `far`.
Our three-point classification agrees with the delivered `three` flag on
98.4 % of attempts; disagreements are shots within ~1 ft of the arc, which is
the same order as the tracking's own positional error.

**Player identity.** Nine ACB players carry two `player_id` values.
`data/player_id_aliases.csv` maps each to a canonical id. Every event table in
this project gains a `<col>_canonical` companion column, and the season
aggregates are additionally collapsed (`*_merged.parquet`) because **all eight
affected pairs that reach the aggregates sit on the same team** — a naive
per-player aggregation double-counts them. See `src/data/aliases.py`.

## 6. Where each column came from

| Provenance | Meaning |
|---|---|
| **Delivered** | present in the SkillCorner files, renamed to snake_case only |
| **Exploded** | a delivered `[x, y]` list split into `_x` / `_y` |
| **Canonicalised** | `*_id_canonical`: a delivered player id mapped through the alias file |
| **Derived** | computed by this project — every one is defined in `docs/METHODOLOGY.md` |

Nothing in this repository invents a field that the source does not support.
Where a concept is useful but absent from the source (roll vs pop, movement
intensity bands, court control, spatial advantage, expected FG), it is computed
here, named distinctly, and labelled in the UI as **not** a SkillCorner metric.
